# Архитектурные решения (ADR-lite)

Краткие зафиксированные решения по проекту Family Tree. При споре «как делаем» — сначала обновите этот файл, потом код и **[mvp-guide/00-schema-and-mapping.md](mvp-guide/00-schema-and-mapping.md)** при изменении схемы данных.

---

## ADR-001 — Поэтапная эволюция вместо «большого взрыва»

**Контекст:** один разработчик, обучение, уже есть рабочий Tkinter + SQLite в корне.

**Решение:** идти по фазам **A → B → C → D → E** ([MVP_TASK_PLAN.md](MVP_TASK_PLAN.md) §0.1). Каждая фаза заканчивается **запускаемым** артефактом.

**Последствия:** не вводить `core/` и User/JWT одновременно; не удалять legacy до появения замены для сценария.

## ADR-002 — Единый источник правды по схеме данных

**Решение:** поля таблиц и смысл связей описывать в **[mvp-guide/00-schema-and-mapping.md](mvp-guide/00-schema-and-mapping.md)**. Примеры в остальном mvp-guide должны с ним совпадать.

**Последствия:** изменение колонок → сначала **00-schema**, затем ORM, домен, DTO, гайд.

## ADR-003 — Вертикальный срез важнее горизонтального слоя

**Контекст:** соблазн сначала написать весь `domain/` без подключения к UI.

**Решение:** при внедрении `core/` брать **одну цепочку** end-to-end: например «список персон» → репозиторий → use case → один вызов из `gui.py`. Затем следующая цепочка.

**Последствия:** меньше «мертвого» кода и раньше видны ошибки границ слоёв.

---

## ADR-004 — `owner_id` и переход к multi-user

**Решение:** колонка `owner_id` у персоны с самого начала (nullable). До auth: десктоп может не фильтровать или трактовать `NULL` как «локальные» записи. После веба: **все** выборки персон/связей с фильтром по владельцу (или явным правилом для `NULL` при миграции данных).

**Последствия:** репозитории сразу проектируются с параметром `owner_id` / `user_id`, даже если GUI пока передаёт заглушку.

---

## ADR-005 — Синхронные репозитории в MVP

**Решение:** репозитории — обычные `def`; FastAPI при необходимости — `run_in_threadpool` или аналог, без `async` ORM в первом релизе API.

**Последствия:** проще отладка и одинаковая модель с Tkinter.

---

## ADR-006 — Граница транзакции

**Решение:** одна **Unit of Work** на HTTP-запрос или на действие пользователя в GUI, когда затрагивается несколько таблиц. Коммит — на уровне **композиции** (use case / сервис приложения / dependency в FastAPI), а не внутри каждого метода репозитория, если нужна атомарность «несколько операций».

**Последствия:** в коде репозиториев из гайда часто есть `commit()` — при росте проекта вынести commit в единое место ([MVP_TASK_PLAN.md](MVP_TASK_PLAN.md) уже упоминает это для DeletePerson).

---

## ADR-007 — Безопасность и секреты

**Решение:** секреты (JWT, SMTP) только из окружения / secret store; не коммитить в репозиторий. CI (GitHub Actions) — через **Secrets**.

**Последствия:** в `Settings` значения по умолчанию только для dev.

---

## ADR-008 — Упаковка и данные пользователя (Windows)

**Решение:** в frozen-сборке БД — в профиле пользователя (`%LOCALAPPDATA%\FamilyTree\...`), не рядом с exe в `Program Files` ([database.py](../database.py), Inno Setup в `installer/`).

**Последствия:** обновление установщика не затирает данные.
